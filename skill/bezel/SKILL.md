# Bezel in this repository

Bezel is a design-token platform. Designers maintain the tokens in the Bezel app; this repo holds an exported copy and generates CSS from it with `@bezel-labs/bezel-kit`.

```
Bezel app (cloud, source of truth)
  -> design-tokens.json          DTCG file at the repo root, exported from Bezel
  -> bezel build                 reads bezel.json for options and output paths
  -> variables.css               one CSS scope per context (:root, .dark, .light, ...)
     contexts.ts, fonts.ts       optional generated TypeScript modules
```

Nothing in this repo pushes back to Bezel. A change that must survive the next sync belongs in the Bezel app.

## Hard rules

1. Never edit a generated file. They start with `/* Generated by bezel — do not edit by hand. */` and live at the paths named in `bezel.json` (`variablesOutput`, `contextsOutput`, `fontsOutput`; default folder `src/bezel/`). `bezel build` overwrites them without asking and they are gitignored.
2. To change a token value or add a variable, edit `design-tokens.json`, then rebuild. Never hand-write the CSS variable.
3. After any change to `design-tokens.json` or `bezel.json`, run the tokens build: `npm run tokens` when that script exists, otherwise `npx bezel build` (use the repo's package manager runner). Confirm the outputs were rewritten before finishing.
4. Only tokens with an `exportName` become CSS variables unless `bezel.json` sets `"includeAll": true`. Adding a token without an `exportName` produces no variable.
5. Never pass `--force` to `bezel init`; it discards the existing `bezel.json`. `--project` and `--tokens-version` update their own keys without it.
6. Local edits to `design-tokens.json` are overwritten by the next sync from Bezel. Tell the user when a change should be made in the Bezel app instead, and never silently sync over their local edits.

## The tokens file

`design-tokens.json` follows the W3C Design Tokens (DTCG) format. Every token is an object with a `$type` and one `$value` per context:

```json
"semantic": {
  "color": {
    "primary": {
      "$type": "color",
      "$root": { "$value": "{base.color.green.500}" },
      "dark":  { "$value": { "colorSpace": "oklch", "components": [0.85, 0.16, 152] } },
      "$extensions": { "com.bezel.app": { "exportName": ["primary", "ring"] } }
    }
  }
}
```

- Context keys (`$root`, `dark`, `light`, or whatever `bezel.json` `contexts` lists) sit inside the token. `$root` is the base; other contexts only need the values that differ.
- `$value` is either a literal (DTCG color, dimension, font family, ...) or a reference like `{base.color.green.500}`. References are resolved to literal values in the generated CSS.
- `$extensions["com.bezel.app"].exportName` is the list of CSS variable names the token emits. One token can emit several (`foreground`, `card-foreground`). An empty list means no variable.
- Groups (`base`, `semantic`, `color`, ...) are plain nesting with no `$type`.

## What to do for common requests

| Request | Edit | Then |
|---|---|---|
| Change a color, size, radius, or font value | The token's `$value` in the right context key (`$root` for every mode, `dark` for dark mode only) | Rebuild |
| A value should differ in dark mode | Add or edit the `dark` key on that token | Rebuild |
| New CSS variable | Add a token with `$type`, `$root.$value`, and an `exportName` (or reference an existing token) | Rebuild |
| Rename a CSS variable | Change the `exportName` entry; update every consumer of the old `--name` | Rebuild |
| New theme or brand context | Add the context to `bezel.json` `contexts` (name -> selector) and add that key to the tokens that differ | Rebuild |
| Change where files are generated | Edit `variablesOutput` / `contextsOutput` / `fontsOutput` in `bezel.json`; update the CSS import | Rebuild, delete the old outputs |
| "Pull the latest tokens" / "sync from Bezel" | See the next section | Rebuild |

Find the token for an existing variable by searching `design-tokens.json` for its name inside an `exportName` array.

## Pulling the latest tokens from Bezel

`bezel.json` `projectId` and `version` (`"latest"` or a published semver) say which Bezel project and snapshot this repo tracks.

With the Bezel MCP connected: call `get-design-tokens-file` with that `projectId` and `version`, write the returned `content` string to `design-tokens.json` verbatim (no reformatting), then rebuild. The `sync-project` prompt walks through this, including linking a project when `projectId` is missing. Never pick a project or version yourself; ask when it is ambiguous.

Without the MCP: ask the user to download `design-tokens.json` from the project in the Bezel app and replace the file at the repo root, then rebuild.

Warn before overwriting a `design-tokens.json` that has local edits.

## With the Bezel MCP connected

Prefer small, targeted calls over reading the whole tokens file:

- `get-project-manifest` first: groups, counts, types, contexts, no values.
- `query-tokens` to find tokens by group, type, name, or `exportName`; `get-token-by-path` for one token with every context value.
- `get-token-bundle` for a curated set per task (`theming-setup`, `button`, `card`, `form`, ...).
- `export-tokens` and `get-framework-overrides` to generate CSS, JS/TS objects, or Tailwind / shadcn / Mantine config from tokens.
- `contrast-check`, `color-convert`, `color-ramp`, `unit-convert` for deterministic math instead of estimating.
- `design-review` to check a component description against the tokens.

See `references/mcp-tools.md` for the full list and `references/bezel-json.md` for every config field.

## Setting up a repo that is not on Bezel yet

Run the `setup-project` tool (or the `/mcp__bezel__setup-project` prompt) and follow it; it installs `@bezel-labs/bezel-kit`, writes `bezel.json`, fetches the tokens, builds, and wires the CSS import. Do not improvise the steps.
